# BMCU Link 次期画面：仕様と技術設計案

状態: 設計案。画面や API は未実装。2026-11-27。対象: `dj-oyu/bambuddy`。

## 1. 目的と前提

印刷中に「今どのフィラメントが使われ、給材と造形が想定どおりか」「何がいつ起きたか」を、小さい画面でも一目で確認する。リアルタイム監視の継続とペットカメラとの共存を優先する。Pico の UDP、既存の保存・ライブ配信を土台とし、画面を開くクライアントが複数あっても受信を待たせない。

対象環境は RDK X5 とブラウザ。1台のプリンターに2台の BMCU が接続される構成を含む。ユーザーが指定するコンパクトさは表示を小さくすることであり、読みやすさや操作対象を犠牲にしない。後述のアラーム、自動停止、実物の形状検査はこの画面の実装範囲外。

### この文書の用語

- **報告値**: Pico/BMCU またはプリンターが送った値。到着時刻と鮮度を持ち、実物の正しさを保証しない。
- **予定**: G-code とそのジョブに付随する割当。実際に実行されたことを意味しない。
- **実行推定**: 報告された印刷中ジョブと層番号に、該当ジョブの予定を重ねた推定。実際の押出や造形品質の検証ではない。
- **不明**: 対応関係、情報、鮮度または信頼できる根拠が不足して判定できない状態。正常や数値0と区別する。

## 2. 構成と基本操作

```text
[プリンター / 印刷中ジョブ]       [接続状態・最終更新・欠損]
[BMCU A: 4スロット] [BMCU B: 4スロット]  [造形の推定プレビュー]
 [選択スロットの小型機構図]                   [層・予定/報告の色と対応]
[過去の重要事象 ⇦] ── A・B / スロット別の出来事 ── [現在]
[選択した事象の詳細 / テキスト一覧]
```

これは情報の優先順位を示すスケッチで、最終ピクセル配置ではない。狭い画面では BMCU、造形、タイムラインを縦に並べ、情報や操作が横にはみ出す場合もキーボードで到達できるようにする。画面を開いた直後に健康状態と現在の給材側を確認でき、詳細は展開する。BMCU、プリンター、ジョブ、プレートの紐付けは明示し、自動で確定できなければ選択または不明とする。BMCU の link index とプリンターの AMS ID は同一と仮定しない。

## 3. 小型 BMCU 表現

- BMCU ごとに4スロットを表示し、現在選択されたスロットだけを強調する。内部のゼロ始まり ID は利用者向け表示と区別する。選択なし、不明、通信断は別状態。
- 選択スロットの pull、motion、pressure を、送り経路や可動部を模した一つの小型図で表す。複数の大きなメーターは作らない。**部品の形、動き、動く向き、スケールは現物とプロトコルの検証後に決める**。機構を事実以上に再現したように見せない。
- pull は既存データの50が中立という意味を保持し、報告値に応じて中立位置から動かす案。motion は定義済みの値だけを対応付け、未知値は不明とする。pressure は単位・符号・意味・表示範囲を確認するまで物理量や圧力の強弱に翻訳しない。null を0として描かない。
- 数値を常時の主表現にせず、状態名と更新時刻を短く添える。数値は詳細表示・アクセシブルな説明・診断として参照可能にする。動きや色だけで状態を伝えない。
- 最新性が失われたら動作を止め、最終値と経過時間を明示する。古い画像を動作中のようにアニメーションしない。減速・停止と実際のモーター停止を混同しない。モーション低減設定では静止図とテキストを使う。

現行 `frontend/src/api/bmcuMonitors.ts` の `motion`、`pullPercent`、`pressure`、`statusAgeS` を起点とする。既存 `faultCount` は CRC/frame エラーの累積であり、機構の故障件数とは扱わない。

## 4. 出来事のタイムライン

グラフの数値推移ではなく、印刷と給材に関する出来事を時間順に提示する。路線図やコミットツリーを参考に、時刻を共有する軸と BMCU/リンク/必要に応じたスロットのレーンで因果関係ではなく所属を示す。分岐線は親子・因果を証明しない。同時刻の密集は束ね、展開して個々のイベント・時刻・対象・種類・詳細を見る。絞り込み、前後移動、取得中、空、失敗を明示する。

- 重要 fault は表示期間の外でも吹き出しで存在を示す。ただし「検索済みの保持期間内で見つかった直近の重要事象」であること、日時、対象、解消済み/未解消/不明を明記する。選択で該当時刻へ移動し詳細を開く。範囲外すべてを調べたかのような件数は出さない。
- 当面の重要事象候補は motion fault の発生/解除、Pico の error/critical、BMCU safety decision とする。重要度の閾値や未解消の定義は firmware と運用で検証する。UDP 欠損や欠落した解除通知がある場合は未解消を断定しない。Bambuddy 由来のイベントは出典を区別する。
- 転送の欠損、再起動、時間順の不確実性、保存期間、集約・間引きが分かるようにする。受信順と発生順は同じとは限らず、sequence の比較は device/boot の範囲でのみ行う。現行描画の欠損の前後15秒は可視化上の目印であり、実際の欠損時間とは断定しない。
- 重要度は色に加えて形と文字で区別。各イベントは操作可能な要素とし、一覧・詳細を読み上げ、キーボードで選択できる。吹き出しが本線や別の重要事象を覆い隠さないよう件数制限と一覧への導線を設ける。

既存の履歴 API は要求した期間のデータを返す。範囲外の重要事象を出すには、権限を適用した別の検索または拡張 API が必要。直近 N 件・対象 device/link・保持期間を制限し、結果の検索範囲と打ち切りを返す。fault の現在状態を別途保持する場合も、根拠の欠落や古さを表示する。これは新規設計であり既存機能ではない。

## 5. 直近20層の造形推定

### 5.1 対象と描画の意味

見たいのはノズルの動きそのものではなく、**その時点までに造形されたと推定されるワークと、選択フィラメントの妥当性**。印刷中のプリンター、ジョブ、プレートが確定したときだけ、そのプレートの G-code を利用する。許可されたアーカイブと対象プリンターを再確認し、印刷中ジョブの結び付きは `running_print_archive(..., by_name=False)` を起点にする。名前だけの推測、プレート候補が複数のままのデフォルト選択、別ジョブのキャッシュ流用は禁止。外部開始やアーカイブ未取得などで確定できない場合は理由を表示し、偽のプレビューを出さない。

Bambuddy の自動印刷用スニペットやフィラメントのアンロード編集は、送信用の一時 3MF に適用され、元アーカイブに反映されない場合がある。図が元アーカイブを使う場合はその出典と、実際に送った G-code の改変内容は未反映である可能性を明示する。改変後のファイルや実行内容と一致すると断定しない。

プリンターが現在層 `L` を報告した場合、完了したと推定する層は **最大20層、`max(1, L-20)` 〜 `L-1`**。印刷進捗率と現在層/総層はそれぞれプリンターの報告値として別々に表示し、不明や古い値を区別する。レイヤー番号の1始まり/0始まりとスライサーのマーカーの対応を実機で検証する。現在層 `L` は途中位置が不明なため、含めるなら「予定」として別の視覚表現にし、全体進捗率から層内座標を補間しない。20層だけの断片でワーク全体が完成したように見せず、表示対象の層範囲と「推定・直近層のみ」を常時表示する。開始直後、層不明、停止・一時停止、復帰、ジョブ変更、層飛び/逆行で状態を再評価する。

基本案は直近層の**押出経路**を俯瞰または軽い斜視の小型プレビューにまとめる。移動のみ・リトラクトは造形面として描かない。輪郭や淡い下地を加える場合も予定形状と区別する。低速端末では2D俯瞰に縮退する。クリックで既存の詳細 G-code ビューアーへ移動できる。表示はカメラ画像や実造形の品質検査ではない。

印刷途中のオブジェクトスキップは、適用開始時点と対象経路が確定できる範囲にのみ反映し、既に印刷した層を遡って消さない。対象や開始時点が不明な場合は、影響範囲を「予定形状・スキップ未反映」とし、造形済みと推定した描画として扱わない。

### 5.2 色とスロット

G-code の論理ツール、印刷ジョブの AMS 割当、プリンターが報告する物理トレイ、BMCU link/slot の明示された対応を、それぞれ別の識別子・観測時刻として扱う。デバイスにより AMS ID の形式が異なり、外部スプール、複数ヘッド、バックアップスプール、交換やスプーフもある。既存の `tray_now` だけで全機種や複数ヘッドの実供給元を決めない。

色は「G-code 上の予定色」と「プリンター/登録情報が報告する現在色」の出典を表示し、光学的に実測した色と呼ばない。過去層を現在のスプール色で塗り替えない。過去時点の対応や色が記録されていなければその範囲を不明とする。塗り分けは論理ツールの変化に対応し、同じ層内の複数色を一色に潰さない。

状態は **一致 / 不一致 / 判定保留**。不一致は同じジョブ・プレート・区間に対する予定と、鮮度の十分な報告および検証済みの対応が矛盾した場合のみ。層内の実行位置が不明で、その層に複数ツールがある場合、切替中、情報の欠落・遅延、外部供給、偽装色や曖昧なマッピングは判定保留とする。BMCU が選択を報告したことと、実際にその材料が押し出されたことは分けて表示する。

## 6. 実現方式と技術スタック

| 領域 | 方針 | 制約・検証事項 |
| --- | --- | --- |
| UI | 既存 React と TypeScript。低頻度の選択、取得状態、操作とアクセシビリティを React が所有 | 表示文言、狭幅、キーボード、低モーションの確認が必要 |
| 小型 BMCU | インライン SVG を主案。形状は静的に構築し、既存のライブ DOM island が所有する属性だけを `requestAnimationFrame` でまとめて更新 | React と直接更新が同じ SVG ノードを同時所有しない。隠れたタブや stale は停止。SMIL/CSS の継続アニメに依存しない |
| ライブ配信 | 既存の共有スナップショット + SSE、低頻度の REST フォールバック | 生 UDP を購読数だけ再パースしない。バッファ上限、遅いクライアント、切断・再接続・鮮度表示を継続 |
| 履歴 | 既存の履歴取得を拡張し、時刻と所属を表す少数の SVG 要素 + 操作可能な HTML 一覧を主案 | 現在値の高頻度更新とは別周期。保持期間内の重要事象検索、ページングと検索打ち切りが必要 |
| G-code 解析 | サーバー側で確定ジョブ/プレートにつき1回の逐次解析。層ごとの簡略化された押出経路と索引を派生キャッシュに保存し、20層分を取得 | 同一キーの同時要求は単一ジョブにまとめる。キャッシュキーに元データの同一性・プレート・パーサーバージョンを含む。変更時無効化 |
| G-code 表示 | ブラウザ Canvas 2D を初期案。必要時に Web Worker / OffscreenCanvas を機能検出し、非対応時は低頻度描画にフォールバック | 表示の基本は小さな2D俯瞰。既存 Three.js 詳細ビューアーを必要時のみ利用。WebGL/Worker を必須にしない |
| 保管と実行 | 既存の設定されたデータ領域に期限付き派生キャッシュ。解析は受信処理と分離した低優先度のワーカー、同時1件を初期案とする | ペットカメラ・UDP ingest を優先。上限・中断・キャッシュ寿命を実機測定後に設定し、上限時は理由を表示 |

これは実装候補で、現行パーサーの完全な再利用や、既存 API が層ごとのバイナリ取得に対応済みという意味ではない。既存 `frontend/src/lib/gcodeToolpath.ts` の挙動とテストを共通の期待値として使い、新しい逐次解析との差分を管理する。ジョブ継続中に全 G-code を毎回取得・解析し直さず、複数クライアントで同じ解析を重複させない。派生キャッシュを永続 DB の唯一の正本にしない。

解析では G0/G1、G2/G3、XYZ 絶対/相対、E 絶対/相対、G92、明示的な層境界、Z-hop、移動、リトラクト、スライサー固有のツール指定を検討対象にする。既存パーサーに対応しない命令や異常なファイルは、部分的な結果を完全な造形と偽らず、非対応または範囲限定として表示する。ファームウェアやスライサー間の方言差を考慮し、Marlin の仕様を Bambu 機にそのまま適用したと仮定しない。

### 資源・安全・権限

- 初期案は解析同時1、ジョブの重複排除、先着要求への共有、最後の購読者の離脱時または印刷切替時のキャンセル、キュー・キャッシュ総量・存続時間の上限。1クライアントだけが離脱した場合、他の購読者の解析を中断しない。上限値は実機測定まで未決定。負荷が高いときはプレビューを遅延または停止し、ライブ受信やカメラを優先する。
- ZIP/3MF の展開後サイズ・エントリ数、G-code 行長、処理時間、円弧分割数、出力頂点・層・リクエストサイズに上限を設け、制限超過や破損は明示する。経路・プレビューは認可された元アーカイブ/プリンターの権限を毎回継承し、キャッシュヒット時も再認可する。生 G-code を実行しない。
- 既存 UDP は認証・再送なし。欠損、起動、描画の遅延や別時刻のデータを一つの同時点と見なさない。ページ閲覧でプリンターを操作・停止しない。MQTT ブローカーの受信確認は Echo が鳴った確認ではない。
- 過去の観測ウィンドウでは約34レコード/秒、8 SSE 接続を約10秒開いた試験で各29更新、受信分の保存を確認したが、長時間・実ブラウザ・カメラ影響は未評価。これを新設計の性能保証としない。
- 2026-11-27 の試作測定では A1 mini の元 3MF（約1.9 MB、G-code 約10.2 MB、500層）を低優先度の別プロセスで解析し、8 SSE 接続を維持した。ベースライン約10秒と解析中約28秒の MJPEG 受信はそれぞれ約29.8 / 30.3 fps、両期間とも UDP 欠損・キュー溢れの増分は0、各 SSE は全期間で約120更新。解析プロセスの最大 RSS は約60 MB。WebRTC フレーム指標は視聴者不在で動いておらず評価外。短時間・単一ファイルの参考値であり、長時間・実ブラウザ・大容量ジョブの性能保証ではない。

## 7. 受け入れ条件

1. 2台の BMCU を個別に表示し、対象の link/slot の所属を誤らない。0、null、未選択、古い値、オフライン、未知 enum を区別し、stale で図の動きが止まる。
2. 低モーション、色覚差、キーボード、読み上げ、狭い画面で状態・重要事象・詳細へ到達できる。SVG の見た目と状態文が矛盾しない。
3. 時間範囲外の重要事象は取得済み範囲・時刻・解消状態と共に表示され、詳細と該当時刻へ移動できる。大量・同時刻・欠損・遅着・検索打ち切りをテストする。
4. ジョブ/プレートの不一致、名前だけの候補、G-code 未取得、権限なし、印刷層不明ではプレビューや一致判定を捏造しない。進捗率と層数の不明・古さをそれぞれ区別する。1層目、20層未満、層切替、同層多色、異常 G-code、途中のオブジェクトスキップで誤表示しない。
5. 過去の色は現在の色に置き換わらない。スロット照合の対応不明、切替中、色偽装、データ stale、欠損で判定保留となる。プレビューが実造形を証明しないことを示す。
6. 典型と大容量のジョブ、同時8クライアント、低速クライアント、タブ非表示、キャッシュ不在・ヒット・期限切れ、解析中断と資源上限を検証する。8接続のうち1つが離脱しても残り7つが同じ解析結果を取得できる。繰り返しの全ファイル取得・解析や購読者ごとのサーバー再解析が起きない。
7. RDK X5 でカメラ稼働時の基準値と新画面使用時を比較し、CPU・RSS/ピーク・I/O・カメラのフレーム落ち・UDP欠損/キュー・SSE 表示鮮度を測定する。対象 G-code、クライアント数、観測時間、印刷状態を記録し、目標値と合否を測定前に合意する。サーバーから描画までの遅延は計測していない場合に主張しない。

## 8. 未確定事項・次の判断

- 実物を模した機構図の正確な構造、pull/pressure の単位・方向、motion enum と鮮度・更新頻度。Pico のバージョンにより異なる場合の仕様。
- プリンター AMS ID と2台の BMCU link/slot の物理対応、ジョブ/プレートを確定できる条件、外部スプールとフィラメント切替の観測可能性。確証がない場合は表示のみで判定保留。
- 重要イベントの対象、解消状態・保持期間外の扱い、タイムラインの期間と上限。UDP が失った fault の復元は別のプロトコル設計が必要。
- 20層分の表現が積層物の確認に十分か、ビューの角度・縮退形式。部分的な形状がワーク全体の見え方を誤らせないか、実データでレビューする。
- 大容量ファイルの分布と、解析・メモリ・ディスク・応答時間の予算。Web Worker / OffscreenCanvas、Canvas 2D と WebGL の選択はブラウザと実機計測の後に確定する。
- MQTT ブローカー、Home Assistant、Echo を使う任意の監視・通知は別途設定と実機検証が必要。2 BMCU からの自動停止も安全検証が終わるまで無効。
